## Persistence, backup and recovery contract

The caller supplies a trusted local data root. Its live database is
`library.sqlite`, with SQLite-managed WAL and shared-memory sidecars. The adapter
enables foreign keys, WAL, `synchronous=FULL`, a 1,000 ms busy timeout and a
1,000-page automatic checkpoint. `database.settings` exposes the effective
settings, which the tests assert. Writes are short synchronous transactions.

Startup accepts only the known version-1 schema and application ID, runs
`quick_check(1)` and foreign-key/head-reference checks, validates all retained
document hashes and schema contents, and verifies asset links and bytes. Only an
absent database file is initialized. An empty existing file, unknown schema,
damaged head, altered document or missing asset stops opening with
`RecoveryRequiredError`; the adapter never resets or migrates it automatically.
Detected document/asset corruption or failed backup integrity validation stops
subsequent repository operations. WAL files are never removed as a repair.

The initial bounds are 128 MiB for SQLite pages, 1 MiB per project document,
1,000 projects, 64 MiB per asset and 512 MiB of indexed asset bytes. Startup work
is bounded by these storage limits, rather than a hard wall-clock deadline.

`putAsset(bytes, expectedSha256, mediaType)` verifies the digest and MIME metadata
syntax, flushes a temporary file and publishes it without overwriting an existing
hash. Files live at `assets/<sha256>`; document paths are portable metadata and
are never used to locate local files. Existing content is checked before reuse.
This method accepts already reviewed bytes: it does not sniff media formats,
establish rights or implement an upload endpoint. Assets remain retained after
removal from the current head, and interrupted writes can leave harmless orphan
files. Garbage collection is not implemented.

`await repository.createBackup()` uses Node's SQLite backup facility, including
committed WAL content. It publishes a checked, closed, self-contained snapshot at
`backups/library-<timestamp>-<uuid>.sqlite`, then retains that snapshot and two
previous snapshots. The copy proceeds in 128-page batches, with at most 1,024
progress callbacks and a cooperative ten-second deadline. SQLite or filesystem
I/O can exceed that deadline between callbacks; it is not a hard execution timer.
Concurrent backup requests, writes through that connection and connection close
are rejected while a backup is running. No automatic retries are performed.

Backups contain the revision library and asset index, **not the asset bytes**.
Keep the data root's `assets/` directory with its backups for offline recovery;
a database file alone cannot recover missing media. The initial adapter retains
all indexed assets, including those referenced only by an older backup.

For explicit recovery, close the original service and call
`restoreBackup(sourceRoot, backupBasename, newDestinationRoot)`. The selected
basename must identify a generated snapshot under the source root's `backups/`
directory, with no WAL/journal dependency. The destination must be absent and
its parent must already exist. Recovery checks the snapshot, copies it and the
indexed hash-verified assets to the new root, then opens and validates the new
repository. It leaves the original database untouched. Missing bytes, corruption
or an existing destination fail; a partially created destination is retained for
diagnosis rather than overwritten on retry. The caller must explicitly select
the recovered root after reviewing the result. No automatic fallback is offered.

The adapter uses the pinned Node `24.22.1` `node:sqlite` API and no native addon.
`DatabaseSync` blocks the service event loop; one local service owns normal
writes and renderer children must receive immutable envelopes. The bounded busy
timeout does not add multiuser collaboration. Keep live storage on a local
filesystem, outside network shares and synchronization folders. Same-user path
replacement races, hardware power-loss behavior and disk exhaustion were not
verified here. No schema upgrades exist yet; any later migration must first
create a verified backup. Portable `.gstory` exchange remains separate work.
