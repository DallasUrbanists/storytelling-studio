## Starting conditions

The real population run requires a technically reviewed D2-12 network study
area and the saved-revision/export mechanisms. Synthetic research schema,
intersection, allocation, and display work can start before the real walkshed is
ready; no synthetic number can become a Maple claim.

The 19 [Day 3 issue bodies](issues-day-3.md) total 675 target minutes, or 11.25
focused contributor-hours for all planned branches. The core first-population
path excludes D3-10 through D3-13 and D3-15/D3-16, which total 210 minutes;
the resulting 465-minute path is 7.75 hours before extra review and waits.
Conditional history/income validation and imagery work remain separate branches.

## Controller execution

The activated controller uses [the execution schedule](execution-schedule.md)
to run independent source, synthetic geometry, UI, and roadway work under their
specific leases. It must not serialize the whole research stream or wait for
history/income/imagery flags before dispatching the first-population path.

Human review of the actual population snapshot becomes a durable scoped GitHub
question after the worker prepares the concrete evidence. Only that approval
and its consumers wait; other eligible work continues, and an authorized answer
matching the result/source/method hashes resumes work automatically.

A false optional flag means the branch was not evaluated under the approved
scope. A source-based rejection requires an actual assessment; neither outcome
can be relabeled as implemented or approved, and imagery import additionally
requires action-specific rights and useful coverage in its accepted receipt.

## Inputs and method

The implementer must follow the selected pipeline in
[research methods](../architecture/research-methods.md), including the exact
no-key American Community Survey 2024 five-year B01003 source and TIGER 2024
block-group geometry. The source period is 2020–2024; this is not a count taken
on one day in 2024 or an up-to-date 2026 population measurement.

The bounded method uses valid polygon intersections and geodesic areas with an
explicit area-weighted allocation assumption. The method retains source units,
overlap fractions, estimates, margins/annotations, missingness, unrounded
contributions, display rounding, and limitations; it must not call an estimated
partial allocation an exact count of residents.

The implementer should use synthetic cases with hand-calculated expected
results first, then real source hashes and the reviewed walkshed. A named human
reviewer approves the precise factual snapshot; an agent's technical validation
and a source URL do not constitute that approval.

## Execute the bounded issues

The lead should route method, comparability, and approval-boundary work to Sol
and known-contract UI/schema work to Terra. The full issue bodies define the
exact dependencies and stop conditions.

| Lane/order | Issues | Result |

| Source contract | D3-01, D3-02 | Typed provenance and one verified Census/boundary snapshot |
| Study area and math | D3-03 through D3-06 | Synthetic-first geometry, partial allocation, reproducible totals, and diagnostics |
| Local research flow | D3-07 through D3-09 | Immutable local job, visible limitations, explicit approval, and stale-state invalidation |

The first-population path must not wait for the conditional history/income or
imagery branch. Unsupported metric/scene types must fail closed until their own
validation exists. The historical scene appears only when the candidate passes
comparability; a documented unsupported comparison leads to omission, while
income is optional for the first Maple film.

Aerial imagery is also conditional on actual rights and useful coverage. The
first film can use the accepted open vector-map baseline when no candidate
passes those gates; the team must record the omission and retain any broader
imagery capability work as separate scope.

## Run the acceptance procedure

After the relevant issues implement and verify the commands, the gate owner
should run the available checks from the repository root.

```sh
npm run check
npm run test:research
npm run test:render-contract
npm run test:smoke
```

The gate owner should complete the following proof of the bounded method.

1. Run hand-checkable no/full/partial overlap, holes, invalid geometry, missing
   data, duplicate-unit, and zero-denominator cases.
2. Reproduce the real population result from retained source, method, geometry,
   and parameter hashes, then inspect at least one full and one partial unit.
3. Show the actual period, estimate wording, scope, coverage, and essential
   limitation on the card and both exported variants.
4. Record the human review of the concrete snapshot, then change a relevant
   source, method, parameter, or study area and confirm the approval becomes stale.
5. Confirm an unapproved or stale claim cannot enter factual export, and any
   included optional claim/imagery has its own appropriate evidence.

Gate E passes the required bounded population pipeline only when those checks
and its actual reviewer record exist. The receipt should separately identify
conditional capabilities as implemented, deferred, unavailable, or omitted with
reason; it must not expand the first-film acceptance criteria silently.

## Stop and hand off

The required milestone remains blocked by a missing or invalid actual walkshed,
unsupported population calculation, incomplete coverage that defeats the claim,
or absent factual approval. Unsupported history or income must not be invented
to fill a scene, and unsupported conditional imagery can be omitted with its
recorded reason.

The worker should save the approved project, stop its own services, and submit
source hashes, result/review snapshots, reproduction evidence, conditional-scope
or source decisions, and proposed documentation changes in its issue receipt.
The coordinator updates [implementation status](../implementation-status.md) and
the shared ledger in the same reviewed pull request; independent synthetic
roadway work continues from its own prerequisites.
